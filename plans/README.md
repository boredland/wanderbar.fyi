## What changed during implementation

Adversarial review (a second model family) caught three things the plans got wrong.
All were verified against the code before acting on them:

- **Plan 005 as written was a regression.** It said "one request per covered
  point per provider". SLF and ALBINA do not answer per point: they publish one
  document for the whole country (`aws.slf.ch/api/bulletin/caaml/en/geojson`,
  `static.avalanche.report/.../EUREGIO_en_CAAMLv6.json`). Fanning out would have
  downloaded the same ~1 MB up to three times on a phone with one bar. Fixed by
  giving `Provider` a `pointQuery` flag: NVE and Avalanche Canada get one request
  per point, SLF and ALBINA get one request carrying every covered point and
  resolve them against the single parsed response. Both paths are now pinned by
  tests (`downloads a country-wide bulletin once`, `asks each sampled point`).
- **Plan 003 was wrong and is rejected.** See the status row. The bug it
  described is real — AVCAN builds `bands` and discards them — but the fix it
  prescribed produces meaningless UI. `bands: []` is now commented as deliberate.
- **Plan 006's allowlist was too broad.** It listed `googleapis.com`, which with
  the dot-anchored match also admits `storage.googleapis.com/<attacker-bucket>`
  and every other Google service a stranger can host a URL on — each of which
  would have received the alarm's signed VAPID header. Narrowed to
  `fcm.googleapis.com` and `android.googleapis.com`, with a test.

Reviewer claims that were **checked and dismissed**:

- *Service-worker PUT would 403.* It does not. Fetch Metadata defaults
  `Sec-Fetch-Site` to `same-origin` and downgrades only on an origin mismatch,
  and the Fetch spec appends `Origin` for any non-GET/HEAD request. Verified
  against both specs and against the running Worker, including the
  `Origin`-only fallback path.
- *`fcm.googleapis.com.` (trailing dot), punycode lookalikes, userinfo
  smuggling.* All already rejected; confirmed by probing the predicate.

Findings the review raised that are **pre-existing** and were left alone (they
are outside these plans' scope, and none was introduced here): the singleton
`idFromName('solo')` Durable Object shared by every visitor; the service worker
caching a redirected localized document under `/`; `resubscribe()` ignoring
`schedule.enabled`; the SLF/ALBINA bbox overlap over eastern Switzerland;
`Date.parse(`${row.ValidTo}Z`)` in the NVE provider; `openDb()` memoising a
rejected promise. The first of those is worth its own plan.

## Follow-ups closed after the first push

- **The browser verification plan 007 could not run** has been done. A cached
  Chrome in `~/.cache/puppeteer` needed only `libasound.so.2`, extracted from
  the .deb into a temp dir rather than installed. A real page's `PUT` and
  bodiless `DELETE` both send `sec-fetch-site: same-origin` and an `Origin`
  header, and both return 200. A fetch issued from inside a real
  `ServiceWorkerGlobalScope` sends `sec-fetch-site: same-origin` too, which
  settles the review's largest worry: push resubscription is not broken. A
  cross-origin `DELETE` never reaches the handler (CORS preflight `OPTIONS`
  404s), and a cross-origin form POST 404s because the route defines no POST.
- **The singleton Durable Object** is fixed. It is now one instance per push
  subscription, named by endpoint. Reproduced first: with two subscribers, B's
  PUT overwrote A's row and B's DELETE removed it entirely, leaving A with no
  wakes and nothing on screen to say so. After the change each keeps its own
  row and B switching off leaves A's intact — verified against a running
  worker. `waker.ts` itself is unchanged; the bug was in addressing, not in the
  object. Stopping a schedule now names its endpoint (`app/lib/wake.ts`), and
  the service worker retires the old endpoint's instance on rotation, which
  also closes the review's finding that a rotation re-enabled notifications the
  reader had switched off.

## Findings considered and rejected

Checked against the source and deliberately **not** planned, so nobody
re-audits them:

- **SSRF in `/api/met`** — not a finding. `app/routes/api/met.ts:6-13` validates
  `lat`/`lon` as finite and in range, then interpolates them into a hardcoded
  `MET_URL`. The upstream host cannot be influenced.
- **XSS via the share-target payload** — not a finding.
  `app/routes/api/share.tsx:20` escapes `<` to `\u003c` before embedding JSON in
  a `<script type="application/json">`, which forecloses the `</script>`
  breakout. The surrounding `dangerouslySetInnerHTML` looks alarming and is
  correct here.
- **Leaflet bloating the main bundle** — not a finding. It is already
  dynamically imported at `app/islands/track-map.tsx:53-54`, deliberately,
  because it touches `window` at module scope.
- **`stitchHourly` iterating only the archive's keys**
  (`app/lib/weather.ts:266`) — latent, not live. Both legs are built by the same
  `coords` helper and request an identical `hourly` variable list
  (`weather.ts:223-226`), so no key can exist in one and not the other today. It
  would become real if the two requests ever diverge; not worth a plan now.
- **`undici` advisories** — dev-tooling only, reached through
  `wrangler → miniflare`. Deployed code runs on workerd's native `fetch` and
  never loads `undici`. Resolve by bumping `wrangler` when upstream ships it.
- **`Response.error()` in the service worker's `staleWhileRevalidate`**
  (`app/sw/index.ts:168`) — not worth doing. Assets are precached at `install`,
  and the README documents precaching as the mechanism that guarantees a cold
  offline start. Returning a synthetic 504 instead would mask a genuinely
  missing asset.
- **NVE returning `bands: []`** (`app/lib/avalanche.ts:187`) — correct, not a
  bug. The NVE endpoint in use carries no elevation split. Explicitly out of
  scope in plan 003 so it is not "fixed".

## Direction — options for the maintainer, not problems

Grounded in repo evidence, offered as choices:

- **Sync when the network returns.** `app/lib/online.ts:6-14` already listens for
  `online`, but `app/islands/track-view.tsx:137-141` refetches on a fixed 30-minute
  interval only. Regaining signal on a ridge leaves stale data for up to half an
  hour. Cheap, and guarded by the existing mid-flight track-swap check at
  `app/lib/sync.ts:84-91`. Trade-off: a burst of syncs on a flapping connection,
  so it should be conditional on the forecast already being `stale` or `expired`.
- **Export the GPX.** `app/lib/store.ts:15` keeps `track.gpxText` verbatim, and
  there are two ways in (upload at `app/islands/upload.tsx`, share target at
  `app/routes/api/share.tsx`) and none out. A client-side Blob download needs no
  server state. Trade-off: one more control on a deliberately spare screen.
- **Share outward.** `navigator.share` could send the track file or the verdict
  line already formatted at `app/islands/track-view.tsx:204-214`, completing the
  inbound-only share integration. Trade-off: the weakest of the three — it adds
  surface to the one-screen design for a capability the OS share sheet partly
  provides already.

None of these contradicts a documented constraint. Deliberately **not**
suggested, because the README rejects them on the record: a routing engine,
extra server state, machine-translating avalanche bulletins, notifying on every
wake, bulk map-tile caching, and folding the avalanche bulletin into `warnings`.
